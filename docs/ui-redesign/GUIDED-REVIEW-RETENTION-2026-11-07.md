# Guided review and completed-original retention

Implements the accepted plan from `97ad022`. This document records the implementation and synthetic checks; publication is recorded separately in the release receipt.

The single and grouped React report destinations now share the existing report controller and guided account, figures, categories, applicable exceptions and final-summary screens. Next writes original review progress only. Finish uses the original atomic financial command, with the existing uncertain-response recovery. Optional categories have explicit resolved/uncategorized versus deferred intent. Completed reports open a result; deferred categories link to original annotation commands without replaying the import. Committed-source re-review uses a separately encrypted, bounded, revision-guarded draft and the original budget save. Activity follow-up retains the original cycle decisions.

Server-derived New / Partly digested / Digested states are distinct from parser/queue states. Automatic preparation remains New. Completion requires current financial or independently parsed no-change evidence and verified whole-file coverage. Required re-review cancels the timer. Complete handling starts a 30-elapsed-day notice period; missing historical timestamps never cause retroactive expiry. Deferred categories, unknown coverage, skipped sheets or months, pending/unsupported activity rows, unhandled cycles, revoked access and live group references prevent removal.

The dedicated transactional retention transition clears encrypted original bytes, parsed drafts and obsolete proposals across the target and linked private staging copies. It retains source IDs/hashes, normalized finances, categories, original commit identifiers and history. Removed sources disappear from active lists and cannot be downloaded or re-parsed. Failures roll back all copies, display a reason and retry. Exact resend acknowledgments and supported freshly parsed equivalent reports retain completion tombstones without creating financial writes or new inbox work. Normal destructive source deletion cannot erase a retention tombstone.

The updated signed installer remains at `/shortcuts/budgit-incoming.shortcut`. Install this revision using the same folder and upload key. Its version-2 catalog validates connection/hash/receipt ownership and distinguishes `stored:true` from strict completed/original-removed acknowledgments with `stored:false` and `cleanupEligible:false`. Old clients fail safely and retain local originals. The public Shortcut still contains no Delete File action. Server retention and device-file retention are separate.

Encrypted historical backups can retain original bytes until their normal expiry. Restore with the current application and retention enabled: source access and the maintenance sweep recheck deadlines before returning originals. For a backup older than a known removal, `restore-check <archive> <private-key> <new.sqlite> <new-report-store.key> <trusted-current.sqlite>` merges authenticated newer tombstones from the explicitly supplied current database. The output is a new file; neither input is modified. An old archive alone cannot know removals that happened after its creation. Keep trusted current retention evidence during recovery. Pre-policy rollback images are only suitable before originals have been removed; later rollback must retain these retention-aware server endpoints.

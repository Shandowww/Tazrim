# Private/shared spaces — implementation checkpoints

Date: 2026-10-26, Asia/Jerusalem. Implementation requested in the existing chat; no new chat, subagents, invitations or live financial migration were created.

## Implemented

- One reusable space namespace contract: personal scopes resolve from the authenticated identity; additional budgets retain their existing budget namespace. Entity references include scope, kind and ID. This does not grant authorization or change vault encryption contexts.
- Budget listing returns only the caller's personal-record existence/revision and accessible budget scopes. Shared plan reads now include the authenticated account ID so the client can detect a changed session between list and plan requests.
- A visible space selector and privacy label on the main screens, including locked budgets. The existing menu selector remains available.
- After joining, the user can start with the shared space or open their private space. New shared participants with no personal saved record receive the same choice on first use of a device. Private setup is available later from space settings; existing personal data opens in place. Shared viewers can manage their own personal data.
- Shared-only mode hides only a known-empty personal budget, and never hides saved/encrypted data. If all additional spaces disappear, the personal space is available again. Choices are device-local and keyed by the authenticated user; the old global selection is deliberately not adopted because its owner is unknown.
- Report intake states the destination space and privacy before file selection. No file is moved across spaces by this change.
- Monthly/card drafts now join the existing switch guards. A refused switch restores the selector without discarding the input. A failed ordinary load preserves the previous usable plan. A changed identity or revoked scope clears the financial display and asks for a fresh page; a failed switch cannot restore a previous scope removed from the latest access list.

## Contracts and compatibility

- Original budget JSON, bank/card IDs, goals, balances, savings ownership, revision checks and explicit-save behavior remain unchanged. No schema migration or automatic reclassification is introduced.
- A scope key is an identity, not permission. Existing server membership checks remain mandatory for reports, raw sources, history, derived data and writes. The new helper is reused by `server/budget-access.mjs` and the space listing.
- Personal setup is optional. It does not require personal salary details to join the household. Choosing personal opens the existing private budget rather than creating another budget or replacing its contents.
- No combined total is released before transfer accounting and duplicate-asset reconciliation are implemented. Additional budgets are not silently relabeled as household budgets based on names or membership counts.

## Seventh milestone — encrypted-space transfer matching, 2026-10-26

Continued from `96996f0`. Matching now supports one encrypted source plus one plaintext source, and two independently encrypted sources. Locked source cards offer a temporary password/recovery-key form inside the transfer overview. Each unlock first rechecks the authenticated identity, access, source revision and current ciphertext, then authenticates/decrypts locally and retains only transfer snippets plus nonextractable keys. It does not switch the active budget, populate its plan, change ordinary account/goal unlock state or save financial records. An already-unlocked active vault can supply the same temporary matching capability; the fetched ciphertext is authenticated again. Refresh reuses temporary keys only for the same key/context and verifies the freshly fetched envelope. Rotated keys require a new unlock.

Encrypted match records use a browser-sealed format with source space IDs, expected revisions, key/context metadata and opaque source tokens outside the ciphertext. Raw source keys/fingerprints, financial amounts, account labels and descriptions stay out of the request. HKDF separates an AES-GCM matching key from an HMAC source-token key for each vault. User-bound HMAC tokens allow duplicate detection without exposing encrypted transaction IDs; plaintext-source tokens are checked against the existing authorized plaintext source. The entire reference pair is encrypted under every encrypted source's derived key, in deterministic source order, with authenticated user, record ID, source metadata and layer binding. A dual-vault match requires both keys to decrypt. The existing server-side encrypted private-record wrapper and recovery-key mechanism remain in place. No new password, raw-key storage, service or paid resource is introduced.

The server continues to enforce user binding, current membership, source revisions, vault key/context, collection revision, one-use source tokens, limits and explicit confirmation. It rejects plaintext references accompanying a sealed request and malformed/canonical-invalid ciphertext. It returns a valid opaque record as **sealed**, rather than claiming to have verified encrypted transaction contents. Only the browser can promote it to a current match, after decrypting and checking both actual source references, fingerprints, directions, exact cents, revisions and source tokens against fresh permitted snippets. Locked records reveal no decrypted references. Changed/revoked sources return only an unavailable private record ID; deletion remains private and possible without unlocking. Unresolved/invalid matches must be opened or removed before creating another, preventing an unknown locked match from being reused silently. No combined total, counterpart, financial adjustment or shared JSON reference is added.

All temporary keys, transfer snippets and decrypted match refs are synchronously released when the overview closes, the app renders another view, the page exits, the account changes or access/authentication requires a fresh page. Entered secrets are cleared before asynchronous work; temporary raw key arrays are zeroed after derivation. Late responses cannot repopulate a closed view. Decrypted plans are temporary local work values and are not retained in matching state. Device/session storage contains no matching secrets or financial snippets. Existing explicit saves, encryption recovery, draft guards and current-budget lock behavior are retained.
